## Details

### P2: Hardcoded dev credentials in source (src/app/login/login-form.tsx:14–28)

```typescript
const DEV_PREFILL = process.env.NODE_ENV !== "production";
const DEV_EMAIL = process.env.NODE_ENV !== "production" ? "admin@civicdemo.com" : "";
const DEV_PASSWORD = process.env.NODE_ENV !== "production" ? "civic-admin-2026" : "";

export default function LoginForm() {
  ...
  const [email, setEmail] = useState(DEV_PREFILL ? DEV_EMAIL : "");
  const [password, setPassword] = useState(DEV_PREFILL ? DEV_PASSWORD : "");
```

**Why P2 (not P0):**
- Gated to dev only: `NODE_ENV !== "production"` is reliable guard
- Not sent to client in production builds
- Uses Supabase test user API anyway (real auth)
- Git history includes the creds, but low-value dummy account

**But still a smell:**
- Credentials visible in source to anyone with repo access
- Accidentally committed to public repo would be a problem
- Better: use Supabase's official test user creation instead

**Fix:** Move to `.env.local.example` (never committed) or Supabase test user:

```typescript
const DEV_PREFILL = process.env.NODE_ENV !== "production";
const DEV_EMAIL = process.env.NEXT_PUBLIC_DEV_EMAIL || "";
const DEV_PASSWORD = process.env.DEV_PASSWORD || "";

// In .env.local (gitignored):
// NEXT_PUBLIC_DEV_EMAIL=admin@civicdemo.com
// DEV_PASSWORD=civic-admin-2026
```

Or use Supabase's test user API:

```typescript
const testUser = {
  email: "test@localhost",
  password: "Testing123!",
};
```

### P2: Missing explicit INSERT deny policies (supabase/migrations/20260527_001_initial_schema.sql)

Classifications and work_orders have RLS enabled but no INSERT policies defined:

```sql
ALTER TABLE classifications ENABLE ROW LEVEL SECURITY;
ALTER TABLE work_orders     ENABLE ROW LEVEL SECURITY;

-- Only SELECT and implicit UPDATE policies; no INSERT
CREATE POLICY classifications_select_staff ON classifications ...
-- Missing: CREATE POLICY classifications_insert ...
```

**Why it's intentional:**
- Classifications are inserted only by the `classify-pipeline` via service-role client
- Work orders are generated by rules engine via service-role client
- RLS default-deny blocks unauthorized INSERTs
- But the error is 404 "Not Found", not a clear "You don't have permission to insert"

**Current behavior (safe but unclear):**
```
User tries: supabase.from("classifications").insert(...)
RLS denies: 404 Not Found
User thinks: Row doesn't exist?
```

Better would be:

```sql
-- Explicit deny with clear semantics
CREATE POLICY classifications_insert_deny ON classifications
  FOR INSERT
  AS (false);

-- Now:
User tries: supabase.from("classifications").insert(...)
RLS denies: 403 Forbidden (or same 404, but via explicit policy)
```

**Fix (optional):** Add explicit policies if you want clearer error messages:

```sql
CREATE POLICY classifications_insert_deny ON classifications
  FOR INSERT AS (false);
CREATE POLICY classifications_update_staff ON classifications
  FOR UPDATE TO authenticated
  USING (
    is_staff() AND EXISTS (
      SELECT 1 FROM reports r
      WHERE r.id = classifications.report_id
      AND r.city_id = current_user_city_id()
    )
  )
  WITH CHECK (
    is_staff() AND EXISTS (
      SELECT 1 FROM reports r
      WHERE r.id = classifications.report_id
      AND r.city_id = current_user_city_id()
    )
  );

CREATE POLICY work_orders_insert_deny ON work_orders
  FOR INSERT AS (false);
```

This doesn't change behavior, but makes intent explicit: "These tables are not directly inserted by users; the service role owns writes."

## Security Strengths (No issues)

### ✓ RLS comprehensive coverage
- Cities: readable by all (public data)
- Users: scoped (own or staff-in-city)
- Reports: scoped (own or staff-in-city)
- Classifications + work_orders: subqueries verify city scope
- Audit log: admin only
- Service-role calls: used only server-side (lib/db, actions, routes)

### ✓ Indexes well-designed
- GiST on geography (reports location, cities boundary, assets location)
- B-tree on common filters (city_id, status, created_at, reporter_id, priority_score)
- No redundant or missing indexes detected

### ✓ Cascades intentional
- `ON DELETE CASCADE` on classifications/work_orders/verifications deletes child rows
- `ON DELETE RESTRICT` on reports→city prevents orphaning

### ✓ Audit logging built-in
- `audit_trigger_fn()` on reports, work_orders captures INSERT/UPDATE/DELETE
- User context via `auth.uid()`, old + new data
- Admin-only via RLS policy

### ✓ Helper functions SECURITY DEFINER
- `current_user_city_id()`, `current_user_role()`, `is_staff()` bypass RLS on users table
- Used safely in RLS policy bodies (no user injection possible)

### ✓ No raw SQL in application code
- All Supabase.js calls use parameterized operators (`.eq()`, `.gt()`, `.in()`)
- No string interpolation into queries (except PostGIS POINT, which is safe)
